## Summary

The desktop language picker offered ~40 languages, but only **three** of them were actually complete. The other 37 locales had been created with a "partial" pattern: 8 of the 36 sections were translated, and everything else silently fell back to English through `defineLocale()`.

This PR brings **every locale to the full structure** and translates what was missing.

| | before | after |
|---|---|---|
| locales with all 36 sections | 3 | **40** |
| leaves per locale (en.ts shape) | 105 – 2539 | **2539** (zh: 2558) |
| strings translated per locale | 105 – 2532 | **2444 – 2512** (97–99 %) |
| localized settings field copy | 0 | **39** (97 labels + 41 descriptions each) |

The settings panel is worth calling out: `FIELD_LABELS` / `FIELD_DESCRIPTIONS` live in a separate English-only module (`src/app/settings/constants.ts`) that every locale imported. The field copy now has a localized counterpart per locale in `src/i18n/field-copy/`, so the settings panel follows the selected language too.

`zh` keeps its `messaging.platformIntro` section — 19 strings that `en.ts` does not have. That is a feature of the Chinese locale, not a defect, and the audit reports it as `+19 extra`.

## How it works

The tooling lives in `scripts/`:

| script | role |
|---|---|
| `i18n_extract_locale.mjs` | TypeScript-AST extractor — lossless, unlike a regex parser (nested templates, multi-line ternaries, arrays, imported constants all survive) |
| `i18n_write_locale.mjs` | writes a locale from the en.ts structure; **parse gate** — a file that does not parse is never written |
| `i18n_translate_locale.py` | batch translation with placeholder masking and a validator that rejects any translation whose interpolations changed |
| `i18n_build_plural_words.py` | the plural-word table — the model treats a ternary as code and refuses to translate it, so the plural forms are translated as words and substituted back |
| `i18n_build_special_words.py` | the labels the model refuses (sentences around an interpolation) |
| `i18n_overlays/<locale>.json` | the hand-authored remainder per locale |
| `i18n_audit_locales.py` | per-locale completeness report |

Two safety properties are worth noting:

- **A locale file that does not parse is never written.** The writer generates the file, parses it with the TypeScript compiler, and aborts on the first diagnostic. The original file stays untouched.
- **A translation with a broken interpolation is rejected.** `${count} ${count === 1 ? 'message' : 'messages'}` must keep exactly its variable names; the plural words inside the ternary may change, the code may not.

## Notes for the reviewer

- The locale files are regenerated, so the diff is large. The structure is mechanical: every locale has the same 2539 leaves as `en.ts`.
- `en.ts` itself is unchanged.
- The translations are machine-generated with a model, then checked by the placeholder validator and the parse gate. A native speaker would probably improve the phrasing — that is a follow-up, not a blocker.
- `src/i18n/field-copy/` is generated by `scripts/i18n_build_field_copy.py`; the English source of truth stays in `src/app/settings/constants.ts`.
