## Grading rubric (Accept / Needs work)

**Accept** requires all of:
- Title carries vuln type + impact (e.g. "IDOR on /api/v1/orders/{id} exposes order history of other accounts")
- Repro steps are self-contained — triage reproduces in under 10 min, copy-pasteable HTTP included
- PoC *shown*, not described (screenshots/output proving data or state change)
- Business impact in one plain sentence
- Fix suggested

**Needs work:** name exactly what's missing (Impact? PoC? Fix?) in the feedback file.

## Core lessons to teach

1. **60-Second Rule.** Triage decides within 60 seconds; accepted reports answer in order: bug type (title), exact endpoint+parameter, numbered repro, visible impact proof, business-impact sentence, CVSS + justification. #1 rejection reason: "cannot reproduce / insufficient PoC".
2. **Impact chaining beats raw severity.** Chain low-severity findings into one critical attack path (e.g. enumeration → info-leak → ATO); write it as an explicit step diagram, stating attacker gain per step. Turns a $500 bug into a $10k payout argument.
3. **Prove code execution by DIFFERENTIAL probing** (Lesson 9, from H1 #3694007 Painless-in-Elasticsearch, $7k). Don't claim "sandbox escape" — isolate it: (a) show the parameter reaches a real engine (raw JSON accepted, output changes); (b) malformed-vs-valid probes locate the *compiler* as the discriminating layer (malformed → 500, valid `"1"`/`"1+1"` → 200, same structure); (c) two requests differing ONLY in the code payload produce inexplicably different output (zero-overlap result sets). Keep every payload harmless + self-limited and state explicit stop-conditions.
4. **A corrected title/severity is NOT a rejection** (Lesson 10, from Cloudflare #3622877 "smuggling"→"request-inspection-bypass", still paid). Describe the exact mechanism you *proved* (not the class name), give a precise blast-radius ("read-only, no ATO, no persistence"), and name the fix in the vendor's own terms (e.g. "enforce RS256 algorithm pinning"). Over-claiming the class only risks credibility.
5. **Missing control on a SIBLING path = the bug** (Lesson 33, MariaDB CONNECT #3836021, CVSS 8.8). When a security control exists on one code path but not its sibling, the ABSENCE is the finding — grep every sink for the guard the engine uses elsewhere (`check_global_access(thd, FILE_ACL)`, `is_secure_file_path`); a control the codebase itself treats as mandatory elsewhere is not a design choice. Canonicalise paths before the check; pre-empt any disputed sibling CVE by naming the boundary YOUR case crosses that it didn't. Same tell as auth-route and JWT-verify — whenever you find one unguarded sink, grep every sibling and diff the guards.
6. **Arithmetic on an untrusted length — always read the DIRECTION** (Lesson 34, MariaDB #3781201). `len - 1` on attacker-controlled length, unsigned → `SIZE_MAX` → OOB read → crash before auth = memory-UNSAFE (pays); contrast the CLAMP flavour that is memory-safe and usually Informative (curl `(size_t)size`). Same "integer bug" headline, opposite outcome — the direction IS the severity. Prove it with the minimal E2E and state preconditions; over-stating them is how a real crash gets downgraded.
7. **Reference-count bugs hide behind REUSABLE lookup keys** (Lesson 35, PlayStation #3320669, $10k). A cleanup path that matches its target by a *recyclable* number (fd, index, slot id) instead of the object lets a name-reuse between set and clear turn a leak into a double-release → UAF. Grep teardown code for `== fd/index/slot`; distinguish the DOUBLE-PUT half (frees live memory → exploitable) from the LEAK half (resource exhaustion). State the platform-specific fault trigger; a UAF double-free is High, not Critical until code exec is shown.
8. **A DROP/revoke that clears SOME but not all of an object's grant rows = privilege escalation via name reuse** (Lesson 36, MariaDB #3908943, High 8.0, no bounty on a VDP). When teardown touches a thing carrying grants/ACLs/memberships, enumerate every row it must clear and DIFF against its sibling drops (`DROP PROCEDURE/FUNCTION/PACKAGE BODY` clean their row; `DROP PACKAGE` didn't) — the "one type lags" result IS the bug. The orphaned row + drop-then-recreate-under-the-same-name (the ordinary deploy pattern) re-attaches the old grantee to a later object that runs with a NEW definer's privileges. Grade the CONSEQUENTIAL row (`PACKAGE BODY` gates execution, not `PACKAGE`); check role propagation. VDP-grade writeup craft: plant a marker in protected data, show both control halves, print grant snapshots, state limitations honestly, disclose AI tooling.

## Pitfalls (Windows file handling)

- **A DUPLICATE concurrent execution of THIS job can complete steps 3–4 while you are still on step 1 — read `max(run)` from the pipeline log BEFORE you draft or append, and never append a run the log already holds.** Observed Run 25 (2026-10-12): a second agent session for the same `bf66bounty01` tick wrote the Run-25 `lessons.md` block (16:25:25), the bank section (16:25:37) and the log record (16:25:52) MID-session, while `cron/executions.db` showed only ONE running `bf66bounty01` execution (mine, claimed 16:23:19) and no second row — i.e. a scheduler-level double-dispatch (gateway ticker + another scheduler, or a retry that did not dedupe), not a visible extra job. `scripts/append_run_log.py`'s `run <= last` guard is the backstop: when the run you were about to log is already present, do NOT pass `--force` — first VERIFY the existing block/record is complete and self-consistent (same archive row count, same lesson numbers, `CRLF==0`, `run==index`), then report the concurrency instead of duplicating. Symptom to recognise: a store's mtime falls INSIDE your own run window yet you did not write it (and its byte size grew between two of your own reads).

- **A POSIX `/tmp` path means TWO different directories depending on which tool resolves it — translate it with `cygpath` before reading it back.** On this host `terminal` (MSYS bash) maps `/tmp` to `%LOCALAPPDATA%\Temp` = `C:\Users\damir\AppData\Local\Temp` (check: `cygpath -w /tmp`), while `read_file` resolves `/tmp/...` to `C:\tmp`. Concrete failure (Run 16, 2026-10-10): `curl -o /tmp/r_3452696.md` succeeded and `grep`/`wc` in the SAME shell saw the file, but `read_file("/tmp/r_3452696.md")` returned `File not found … similar_files: ['C:/tmp\\body26.md', …]` — it looked in `C:\tmp`, which held unrelated scratch from older sessions. Fix: after fetching into `/tmp` from `terminal`, read it back via the translated path (`C:/Users/damir/AppData/Local/Temp/<name>`, from `cygpath -w /tmp`), or fetch straight to an absolute Windows path. This is the mirror image of the `write_file`→`C:\tmp` trap at the bottom; when a scratch file looks "missing", work out WHICH `/tmp` you actually wrote to before re-running anything.

Three more Windows/quoting traps (all hit on 2026-10-10, Run 18):

- **`curl -o <path>` needs the NATIVE Windows path — an MSYS `/c/...` destination fails with `curl: (23) Failed writing received data`.** `curl.exe` is a native binary, so MSYS does NOT translate its arguments: `-o /c/Users/damir/AppData/Local/Temp/x.md` is handed over literally and curl tries to create `C:\c\Users\...` → exit **23**, no file, while `mkdir -p /c/...` (a bash builtin) succeeded in the SAME command. Symptom to recognise: `EXIT:23` + `No such file or directory` on the very next `wc`.
