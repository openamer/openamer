**Engineering note — Sep 13, 2026: the training loop that had never trained (a silent-death bug class)**

This one is worth writing down because it failed *completely* and *quietly*, and a status report would have called it "healthy."

**Symptom.** The `auto_retrain` cron job ran on schedule, returned "success," and emitted only a warning — but no training ever happened. Not once. Every retrain silently died.

**Root cause.** The cron wrapper executes under the agent venv (`openamer-agent/venv`, `huggingface-hub 1.2.3`). `auto_retrain` launched its training children (`distill_sft` / `finetune_cpu`) with `sys.executable` — i.e. the *agent* interpreter. So the training subprocess resolved `transformers`' `huggingface-hub>=1.5.0` requirement against the wrong environment and died instantly with an `ImportError`. The parent saw a non-zero child and reported a warning; nothing escalated; the loop that was supposed to improve the model was a no-op.

**The same bug class, second surface.** Even pointing at the right interpreter wasn't enough: the agent shell exports a `PYTHONPATH` that **shadows the training venv's `site-packages`**. Same class of bug — "the process is not actually running in the environment you think it is" — reached through an env var instead of the interpreter path.

**Fix.**
- `_train_python()` picks `$OPENAMER_HOME/venv` (hub 1.30.0) with fallbacks to a venv beside the training dir and the agent venv, overridable via `OPENAMER_TRAIN_PYTHON`.
- `sh()` strips `PYTHONPATH` from the child env.
- The chosen interpreter is now **logged**, so the next failure is attributable instead of invisible.
- `test_auto_retrain.py` (7 tests) pins no bare `sys.executable`, the lookup order, the `PYTHONPATH` strip, and non-zero-exit propagation. The two training suites run 18/18 in 0.22s.

**Take-away for builders of self-improving agents:** "the job ran" is not "the job did anything." A training loop that dies on an import error and reports a warning is indistinguishable from a training loop that has nothing to do — and the second is expected, so you stop looking. Two defences: (1) log the environment you actually resolved (interpreter path, package manager), so mis-routing is visible; (2) make the child's non-zero exit a hard failure, not a warning.
